# lens：核查（交叉验证承重数字）

> equity-thesis-cn 的核查子 agent 读本文件执行。**不覆盖任何一节，校验全部五份 findings。**
> 定位：在编排器下笔之前，把"错了就会翻转判断"的数字逐条回原文核实。
> 时序：串行，五份 findings 到齐后、综合成稿之前。

## 你不做什么（先划边界）

- **不写报告、不写观点、不写散文。** 你的输出是核实结果，不是分析。
- **不 WebSearch。** 许可数据源只有三个：`data/{SYMBOL}/`、年报 PDF、档案人工注入区。
- **不重做子 agent 的活。** 你不负责补充发现，只负责核实已有发现。
- **不"顺手改进"。** 发现 findings 有遗漏，报告给编排器，由它决定补派谁。

## 读什么

- `reports/{SYMBOL}_thesis_{报告日}/findings/*.md` 五份（你的核查对象）
- `data/{SYMBOL}/annual_pdf/*.pdf`（**近 3 年年报都在**，跨期核对用 Read 的 pages 参数）
- `data/{SYMBOL}/basic.json`、`aggregate.json`、`annual.json`（原始数据比对）

## 什么是"承重数字"（编排器会指定 5–8 条，你也要自己找）

一个数字是承重的，当且仅当：**它错了，某一节的判断方向会反过来。**

优先核这几类——它们是实测里最容易出错的：

1. **正负号**。年报表格里负数常写成 `-1,234`、`(1,234)`，或排版中负号单独占一行与数字错位。
   **子公司分析表、减值损失、经营性应付项目变动、汇兑损益**是重灾区。
2. **数量级**。万元 / 元 / 亿元三种单位在同一份年报里混用。差 10 倍或 100 倍的读数极常见。
3. **列错位**。宽表（如"主要控股参股公司分析"有 9 列）容易把「净资产」读成「净利润」、把「营业利润」读成「净利润」。
4. **口径同名异物**。"扣非净利润" vs "剔除股份支付费用后的净利润" vs "归母净利润"——名字接近、数值不同、用途完全不同。激励方案的考核口径尤其容易张冠李戴。
5. **官方比率 vs 报表重算**。数据源给的毛利率/费用率与用原始报表重算的对不上时，以重算为准，并报告差异幅度与可能来源（重分类？口径？）。

## 三条判定纪律

**一、常识矛盾优先查。** 核查的第一动作不是逐条比对，是**先扫一遍找不可能的数**：
- 投入期业务出现 70% 净利率
- 一家亏损公司的子公司净利率高于母公司数倍
- 分部收入加总不等于合计
- 增长率与前后两期绝对值算不出来

这类矛盾是错误最可靠的指示器，比逐条核对效率高得多。

**二、区分"公司没披露"与"我没查到"。** 这两者对判断的含义完全不同：
- 公司没披露 → 是信息缺口，进档案「未决疑问」，可以在正文明说"公司未披露"
- 我没查到 → 是我的能力问题，不能写成"公司未披露"

**报告时必须明确说是哪一种。** 说不清就说"无法区分"。

**三、看不清就提高分辨率。** PDF 表格排版错位时，用 `pdftoppm -r 400` 渲染成图再 Read 逐格比对。
不要靠 `pdftotext` 的一次输出下结论——**负号丢失和列错位正是它最常见的失败模式**。

**四、核完"抄对没有"，再判"这个数在外面算什么水平"。**

前三条纪律都在解决同一个问题：数抄对了没有。但**一个数逐字核实无误，不等于它能拿来当尺子。**

每个承重数字核完，再给它归一次类（五选一），只看参照系来自哪里，与数本身对错无关：

| 参照系类型 | 判据 |
|---|---|
| **外部·可回溯** | 有可比同业/同板块的同一口径数，且**来自本地数据层的直接进此档**；靠搜索得到的**需 ≥2 个独立来源交叉对得上**才进此档 |
| **外部·单源未交叉** | 有外部的同口径数，但只有一个来源，未交叉验证 |
| **外部但口径存疑** | 有外部数，但口径不一致（含"宽池子且池内无同品种"） |
| **私有基准** | 参照系由标的公司或其委托方产生——独立技术报告、招股章程里的委托咨询、公司自己的规划与指引 |
| **无参照系** | 压根没有可比对象 |

五档与 `tools/benchmark_lib.py` 的 `STRENGTHS` 逐字节相同（中间那一点是 U+00B7 的「·」，
不是别的点）——档位串写错一个码位，交付前硬门解析时会静默把这一行当成不存在的档位丢掉，
参照系文件照写不误、硬门却当它没发生。

**这一步不搜外部数据**（你不 WebSearch），只做归类。归类结果的用处是让成稿 agent 知道
哪些判断是悬空的：**当一节的核心结论压在「私有基准」或「无参照系」的数上时，
那一节的结论必须在正文里声明这个限制，不能当成已证实的事实用。**

**为什么加这一条（实测依据）**：03858 那一轮，五条承重数字全部回原文核实通过——
ITR 税后 NPV 四档贴现率、ITR 排产表、F&S 成本区间、港股 72 家 PE 中值、卖方一致预期。
但按上表归类：前三条是**私有基准**（全部出自同一份招股章程），第四条是**无参照系**
（池内一家钨矿同业都没有），第五条是外部但口径存疑。**没有一条是「外部同口径」。**
而全篇的空头结论压在第一条上——"市值是 ITR 税后 NPV 的 2.31–3.25 倍，所以贵"。
这个判断的成立与否取决于同板块在什么倍数交易，而那个数从头到尾没有出现过。
**核查全部通过，判断照样悬空。**

## 输出契约

**不写 findings 文件**（你没有自己的发现）。直接返回：

```
## 核实结果

### 承重数字 N：<一句话说这是什么数>
**结论**：<确认无误 / 修正为 X / 未披露 / 未查到>
**原文抄录**：<逐字抄，含单位与正负号>
**出处**：年报 p.XX / {file}.json 字段
**参照系类型**：外部·可回溯 / 外部·单源未交叉 / 外部但口径存疑 / 私有基准 / 无参照系（并用一句话说参照系是什么）
**若首轮有误**：错在哪一类（符号 / 数量级 / 列错位 / 口径 / 重算差异）

### ...

## 未能核实项
- <项>：说明是「公司未披露」还是「我没查到」

## 新发现的矛盾（如有）
- <findings 之间互相打架、或与原始数据打架的地方>

## 已核实清单（编排器写稿时直接对照这张表，务必列全）
| 数字 | 核实后的值 | 出处 | 参照系类型 |
|---|---|---|---|
| <一句话说这是什么数> | <含单位与正负号> | 年报 p.XX / {file}.json 字段 | 外部·可回溯 / 外部·单源未交叉 / 外部但口径存疑 / 私有基准 / 无参照系 |
```

**最后那张「已核实清单」是给编排器用的**：它写稿时会拿每个承重数字来这张表里对，
对得上就敢用、对不上就得标「未核实」或再派你一次。表里少一行，编排器就多一个没法确认的数。
所以**凡是你这轮真的核过的，无论结论是"确认无误"还是"修正为 X"，都要落进这张表**——
修正过的填修正后的值。

## 核查完之后（编排器的动作，写在这里以免遗漏）

编排器收到核查结果后必须做两件事：

1. **就地修正 `findings/*.md`**，改处标一行"（YYYY-MM-DD 复核修正）"。
2. **正文末尾留一节「数据核查记录」**，列出改了什么、改前改后、错误类型。

**改动要留痕。** 悄悄改掉等于把这道工序的价值扔了——留痕才能让下一期知道哪类数字在这只票上容易读错，进而写进档案的「口径修正」。
